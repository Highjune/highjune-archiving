# 모니터링 시스템 설계

## 개요

tennis-record-k 프로젝트에 로그 수집 및 서버 모니터링 시스템을 구축하기 위한 설계 문서입니다.

## 목표

1. **로그 수집 및 조회**: 애플리케이션 로그를 중앙 집중화하여 검색/분석
2. **서버 모니터링**: CPU, 메모리, 디스크 등 시스템 리소스 모니터링
3. **컨테이너 모니터링**: Docker 컨테이너별 리소스 사용량 추적
4. **알림 시스템**: 임계치 초과 시 알림 발송 (선택)

## 현재 인프라

| 항목 | 상태 |
|-----|-----|
| 서버 | Intel 미니PC, Ubuntu |
| RAM | 16GB (가용 ~12GB) |
| Disk | 468GB (가용 ~415GB) |
| 컨테이너 | snt-app, tennis-mysql, jenkins-server |

## 후보 스택 비교

### Option 1: ELK Stack

**구성**: Elasticsearch + Logstash + Kibana

```
┌─────────────┐     ┌─────────────┐     ┌─────────────┐
│   Kibana    │◄────│Elasticsearch│◄────│  Logstash   │
│  (시각화)    │     │ (저장/검색)  │     │  (수집)     │
└─────────────┘     └─────────────┘     └─────────────┘
                                              ▲
                                              │
                                    ┌─────────┴─────────┐
                                    │   snt-app 로그    │
                                    └───────────────────┘
```

| 구성요소 | 역할 | 필요 RAM |
|---------|-----|---------|
| Elasticsearch | 로그 저장, 전문 검색 | **4-8GB** |
| Logstash | 로그 수집, 파싱, 변환 | 1-2GB |
| Kibana | 시각화, 대시보드 | 1GB |
| **총합** | | **6-11GB** |

**장점**:
- 강력한 전문 검색 (Full-text search)
- 복잡한 로그 분석 가능
- 풍부한 시각화 옵션
- 대규모 데이터 처리에 최적화

**단점**:
- 리소스 소비가 매우 큼 (홈서버에 부담)
- 설정 및 운영 복잡도 높음
- 메트릭 수집은 별도 구성 필요 (Metricbeat)

**적합한 경우**:
- 대량의 로그 데이터 처리 필요
- 복잡한 로그 검색/분석 요구
- 충분한 서버 리소스 보유

### Option 2: PLG Stack (추천)

**구성**: Prometheus + Loki + Grafana

```
┌─────────────────────────────────────────────────────────────┐
│                      Grafana (시각화)                        │
│                     http://server:3000                       │
└────────────────────┬────────────────────┬───────────────────┘
                     │                    │
           ┌─────────▼─────────┐  ┌───────▼────────┐
           │    Prometheus     │  │      Loki      │
           │   (메트릭 저장)    │  │   (로그 저장)   │
           └─────────┬─────────┘  └───────┬────────┘
                     │                    │
    ┌────────────────┼────────────────────┼────────────────┐
    │                │                    │                │
┌───▼───┐      ┌─────▼─────┐        ┌─────▼─────┐    ┌─────▼─────┐
│ node  │      │  snt-app  │        │ Promtail  │    │ cAdvisor  │
│exporter│     │ /actuator │        │(로그수집)  │    │(컨테이너) │
│(시스템)│      │ /metrics  │        └───────────┘    └───────────┘
└───────┘      └───────────┘
```

| 구성요소 | 역할 | 필요 RAM |
|---------|-----|---------|
| Prometheus | 메트릭 수집 및 저장 | ~500MB |
| Loki | 로그 수집 및 저장 | ~256MB |
| Grafana | 시각화 대시보드 | ~256MB |
| Promtail | 로그 수집 에이전트 | ~50MB |
| node_exporter | 시스템 메트릭 | ~20MB |
| cAdvisor | 컨테이너 메트릭 | ~100MB |
| **총합** | | **~1.2GB** |

**장점**:
- 경량 (ELK 대비 1/5 ~ 1/10 리소스)
- Spring Boot Actuator + Micrometer 표준 연동
- Docker 친화적
- 로그 + 메트릭 통합 시각화
- 알림 기능 내장

**단점**:
- 로그 전문 검색 기능은 ELK보다 제한적
- 복잡한 로그 분석에는 부적합

**적합한 경우**:
- 제한된 서버 리소스
- 메트릭 + 로그 통합 모니터링
- Spring Boot 애플리케이션

### Option 3: Grafana Cloud (SaaS)

**구성**: Grafana Cloud Free Tier + 로컬 에이전트

```
┌─────────────────────────────────────────────┐
│            Grafana Cloud (SaaS)              │
│  - Prometheus (호스팅)                        │
│  - Loki (호스팅)                              │
│  - Grafana (호스팅)                           │
└─────────────────────┬───────────────────────┘
                      │ (데이터 전송)
                      │
    ┌─────────────────┼─────────────────┐
    │                 │                 │
┌───▼───┐       ┌─────▼─────┐     ┌─────▼─────┐
│Grafana│       │ Promtail  │     │  snt-app  │
│ Agent │       │(로그수집)  │     │ /metrics  │
└───────┘       └───────────┘     └───────────┘
```

| 항목 | Free Tier 제한 |
|-----|---------------|
| 메트릭 | 10,000 series |
| 로그 | 50GB/월 |
| 보존 기간 | 14일 |

**장점**:
- 로컬 리소스 최소화 (에이전트만)
- 관리 부담 없음
- 무료 티어로 시작 가능

**단점**:
- 데이터가 외부로 전송됨
- Free Tier 제한 있음
- 인터넷 연결 필수

---

### Option 4: 최소 구성 (단계적 도입)

**Phase 1**: 메트릭만 먼저
```
Prometheus + Grafana + node_exporter
```

**Phase 2**: 로그 추가
```
+ Loki + Promtail
```

**Phase 3**: 컨테이너 모니터링
```
+ cAdvisor
```

**Phase 4**: 알림 추가
```
+ Alertmanager
```

## 기술 키워드 정리

### 로그 수집 (Log Aggregation)

| 키워드 | 설명 | 특징 |
|-------|-----|-----|
| **ELK** | Elasticsearch + Logstash + Kibana | 강력한 검색, 무거움 |
| **Loki** | Grafana Labs의 로그 시스템 | 경량, 라벨 기반 인덱싱 |
| **Fluentd** | 로그 수집기 (CNCF) | 플러그인 풍부, 범용 |
| **Fluent Bit** | Fluentd 경량 버전 | IoT/엣지에 적합 |
| **Promtail** | Loki 전용 로그 수집기 | 경량, Docker 친화적 |
| **Filebeat** | ELK용 로그 수집기 | Logstash보다 가벼움 |

### 메트릭 수집 (Metrics Collection)

| 키워드 | 설명 | 특징 |
|-------|-----|-----|
| **Prometheus** | 시계열 메트릭 DB | CNCF 표준, Pull 방식 |
| **InfluxDB** | 시계열 DB | Push 방식, SQL-like 쿼리 |
| **node_exporter** | 시스템 메트릭 수집 | CPU, 메모리, 디스크 |
| **cAdvisor** | 컨테이너 메트릭 | Docker 리소스 모니터링 |
| **Micrometer** | Java/Kotlin 메트릭 라이브러리 | Spring Boot 표준 |
| **Actuator** | Spring Boot 모니터링 | /actuator/metrics 엔드포인트 |

### 시각화 (Visualization)

| 키워드 | 설명 | 특징 |
|-------|-----|-----|
| **Grafana** | 대시보드 플랫폼 | 다양한 데이터소스 지원 |
| **Kibana** | ELK 시각화 | Elasticsearch 전용 |

### APM (Application Performance Monitoring)

| 키워드 | 설명 | 특징 |
|-------|-----|-----|
| **Pinpoint** | 네이버 오픈소스 APM | 분산 추적, Java 특화 |
| **Jaeger** | 분산 추적 시스템 | CNCF, OpenTracing |
| **Zipkin** | 분산 추적 시스템 | Twitter 개발 |
| **OpenTelemetry** | 관측성 표준 | 메트릭+로그+추적 통합 |

### 알림 (Alerting)

| 키워드 | 설명 | 특징 |
|-------|-----|-----|
| **Alertmanager** | Prometheus 알림 관리 | 중복 제거, 그룹핑 |
| **PagerDuty** | 인시던트 관리 | 온콜 스케줄링 |
| **Slack Webhook** | 슬랙 알림 | 간편한 연동 |

## 추천 방안

### 홈서버 환경에서의 권장 스택: **PLG Stack**

**이유**:
1. 리소스 효율: 전체 ~1.2GB RAM으로 운영 가능
2. Spring Boot 표준 연동: Actuator + Micrometer
3. 통합 시각화: 로그 + 메트릭을 Grafana에서 한번에
4. Docker 친화적: 컨테이너로 쉽게 배포
5. 확장성: 필요시 컴포넌트 추가 용이
